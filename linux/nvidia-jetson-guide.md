# Посібник з NVIDIA Jetson Система

Chloros на NVIDIA Jetson забезпечує обробку мультиспектральних зображень на периферії — у польових умовах, на безпілотних літальних апаратах та у віддалених установках. Chloros 1.3.0 визначає модель Jetson під час запуску та оптимізує стратегію обробки відповідно до виявленого апаратного забезпечення. **Ручне налаштування не потрібне.**
{% hint style="info" %}
**Пакет Jetson 1.3.0 виконує обробку на графічному процесорі Jetson.** `chloros_1.3.0_arm64_jp6.deb` створено для JetPack 6 і використовує CUDA-версію PyTorch від JetPack 6, тому обробка, включаючи алгоритм Texture Aware debayer, виконується на графічному процесорі Orin. Пакет не містить самого CUDA: він використовує бібліотеки CUDA та cuDNN, які встановлює JetPack 6 (`sudo apt install nvidia-jetpack` на образі, де їх немає). Якщо графічний процесор з підтримкою CUDA недоступний, обробка виконується на центральному процесорі, а Texture Aware використовує стандартний дебейер.
{% endhint %}

## Підтримувані моделі Jetson

| -------------------- | -------------- | ------------------------------------------------------- | -------------------------------------------------------- |
| **Jetson AGX Orin**  | 32–64 ГБ спільного | `GPU_PARALLEL` (2 робочі процеси)                              | Максимальна продуктивність, великі набори даних                      |
| **Jetson Orin NX**   | 8–16 ГБ спільного | `GPU_PARALLEL` (2 робочі процеси, 16 ГБ) / `GPU_SINGLE` (8 ГБ)   | Основна рекомендація для розгортання в польових умовах              |
| **Jetson Orin Nano** | 8 ГБ спільної пам’яті     | `GPU_SINGLE` (1 робочий процес, послідовний)                     | Початковий рівень периферійних обчислень                                 |

{% hint style="info" %}
Пакет Linux для архітектури arm64 вимагає **JetPack 6**, який доступний на пристроях сімейства Jetson Orin. Старіші моделі (Nano, TX2, Xavier NX) не можуть працювати з JetPack 6 і не підтримуються поточним пакетом.
{% endhint %}

## Вимоги

* **JetPack 6.x** (рекомендується найновіша версія)
* **NVIDIA CUDA та cuDNN** із JetPack 6 (`sudo apt install nvidia-jetpack`, якщо у вашому образі їх немає)
* **Платний план Chloros+** — рівень Copper або вище (необхідний для доступу до всіх CLI/SDK; перевірка здійснюється на стороні сервера)

## Встановлення

```bash
# Install the arm64 .deb package (JetPack 6) -- apt, not dpkg -i, so the
# Python SDK's requirements (python3-numpy, python3-requests) come too
sudo apt install ./chloros_1.3.0_arm64_jp6.deb

# Verify installation
chloros-cli --version    # prints "Chloros CLI 1.3.0"
python3 -c "import chloros_sdk; print(chloros_sdk.__version__)"   # the .deb installs the SDK

# Run system diagnostics
chloros-cli selftest
```

`.deb` встановлює SDK-Python для системи `python3`, що відповідає цій збірці. Лише у virtualenv потрібно встановити вбудований файл wheel: `pip install /usr/lib/chloros/sdk/chloros_sdk-*.whl` (повністю офлайн). Загальні деталі щодо встановлення в Linux, розташування файлів та усунення несправностей див. у розділі [Встановлення в Linux](linux-installation.md).

{% hint style="info" %}
**Більше немає розпакування під час запуску.** Починаючи з версії 1.3.0, бекенд та інтерфейс командного рядка (CLI) встановлюються у розпакованому вигляді в каталозі `/usr/lib/chloros/`, тому вони більше не розпаковуються у тимчасовий каталог під час кожного запуску. Тимчасові файли, як і раніше, автоматично зберігаються в `/mnt/ssd/tmp`, якщо ця папка існує; в іншому випадку ви можете вказати `TMPDIR` як шлях на вашому NVMe (`export TMPDIR=/mnt/nvme/tmp`).
{% endhint %}

## Динамічна адаптація обчислювальних ресурсів на Jetson

### Як це працює

Під час запуску Chloros створює профіль вашої системи:

1. **Виявляє модель Jetson** за допомогою `/proc/device-tree/model`
2. **Зчитує доступну спільну пам'ять GPU/CPU** (Jetson використовує уніфіковану пам'ять)
3. **Запитує PyTorch, чи можна використовувати CUDA** — якщо встановлено CUDA та cuDNN з JetPack 6, це можливо
4. **Автоматично обирає стратегію обробки** (`GPU_PARALLEL`, `GPU_SINGLE` або `CPU_PARALLEL`) та кількість робочих процесів

Рішення залежить від **загального обсягу спільної оперативної пам'яті**, а не від назви моделі:

* **При загальному обсязі оперативної пам'яті менше 12 ГБ**(усі Jetson з 8 ГБ):**1 робочий процес — цілеспрямована послідовна обробка**. Обсягу пам'яті недостатньо для одночасного виконання декількох робочих процесів, тому зображення обробляються по одному. На пристроях Jetson з**8 ГБ або менше** потік 3 повністю оминає пул робочих процесів і виконує обробку кожного зображення в рамках одного процесу. У логах серверної частини ця стратегія має назву `GPU_SINGLE`.
* **12 ГБ або більше**(Orin NX 16 ГБ, AGX Orin): об’єднана пам’ять відповідає вимогам для `GPU_PARALLEL`, але кількість робочих процесів**обмежена до 2 на Jetson** — графічний процесор, оперативна пам'ять робочих процесів та їхні контексти CUDA для кожного робочого процесу використовують один і той самий спільний пул, тому збільшення кількості робочих процесів підвищує ризик помилок через брак пам'яті.
* **Відсутність працездатного CUDA** (відсутні бібліотеки CUDA для JetPack): `CPU_PARALLEL` при 12 ГБ або більше, нижче наведено один образ за раз.

Ви можете замінити автоматичний вибір за допомогою змінної середовища `CHLOROS_STRATEGY` — див. [Динамічна адаптація обчислень](../processing-architecture/dynamic-compute-adaptation.md#manual-strategy-override).

### Поведінка для окремих моделей

| Модель Jetson                | Стратегія       | Робочі процеси | Виконання                                      |
| --------------------------- | -------------- | ------- | ---------------------------------------------- |
| **Jetson Orin Nano 8 ГБ**    | `GPU_SINGLE`   | 1       | Послідовний цикл у процесі (`tiled_gpu` за умови нестачі пам’яті) |
| **Jetson Orin NX 8 ГБ**      | `GPU_SINGLE`   | 1       | Послідовний цикл у процесі                     |
| **Jetson Orin NX 16 ГБ**     | `GPU_PARALLEL` | 2       | Паралельні робочі процеси, шлях `fused_gpu`  |
| **Jetson AGX Orin 32–64 ГБ** | `GPU_PARALLEL` | 2       | Паралельні робочі процеси, шлях `fused_gpu`  |

Ключовою відмінністю між платформами є **обсяг пам’яті**. Jetson з 8 ГБ пам’яті під час високого навантаження має обробляти зображення по одному, використовуючи ефективний з точки зору пам’яті підхід з розбиттям на фрагменти, тоді як Orin з 16 ГБ і більше може одночасно обробляти 2 зображення на графічному процесорі за допомогою злитого конвеєра з вищою пропускною здатністю.

### Бюджет графічного процесора для кожної моделі

Кожна модель Jetson також має апаратний профіль, який обмежує обсяг ресурсів спільного пулу, що може бути задіяний для обробки, та масштабує розміри пакетів:

| Модель | Верхня межа бюджету графічного процесора | Множник розміру пакета | Зарезервовано для системи/дисплея |
| --- | --- | --- | --- |
| **Jetson Orin Nano** | 70% | ×0,8 | 2,0 ГБ |
| **Jetson Orin NX** | 75% | ×1,0 | 3,0 ГБ |
| **Jetson AGX Orin** | 80 % | ×1,5 | 4,0 ГБ |

Профіль коригується відповідно до виявленого обсягу оперативної пам’яті: для пристроїв Jetson, що повідомляють про **16 ГБ або більше**, множник розміру пакета збільшується на ×1,2. Базовий розмір пакета до застосування множників становить 8 зображень.

Повну довідку щодо адаптації обчислювальних потужностей див. у розділі [Динамічна адаптація обчислювальних потужностей](../processing-architecture/dynamic-compute-adaptation.md).

## Обмеження частоти графічного процесора для Texture Aware на Nano та Orin Nano

Альгориtm дебейєрингу Texture Aware виконує інференцію нейромережі на GPU, що може викликати **попередження про перевищення струму**на моделях Jetson з низьким енергоспоживанням (клас 10–15 Вт) при повній тактовій частоті GPU. При передачі `--debayer texture-aware` на**Jetson Nano або Orin Nano**, CLI перевіряє максимальну частоту графічного процесора та обмежує її до **510 МГц** (510000000), якщо поточна частота вища:

* Якщо CLI може записати значення частоти графічного процесора у вузол sysfs, обмеження **застосовується автоматично**, і на екрані з’являється підтвердження.
* Якщо ні (потрібні права root), CLI виводить точну команду `sudo` для ручного застосування обмеження, чекає деякий час, щоб ви могли її прочитати, а потім продовжує роботу — обробка все ще триває, але можуть з’являтися попередження про перевищення струму.

Щоб самостійно застосувати обмеження перед обробкою:

```bash
echo 510000000 | sudo tee /sys/devices/platform/bus@0/17000000.gpu/devfreq/17000000.gpu/max_freq
```

Моделі з більшою потужністю (Orin NX 25 Вт, AGX Orin 60 Вт) працюють на повній швидкості графічного процесора; обмеження не застосовується. Стандартний дебейер ніколи не запускає обмеження на жодній моделі.

{% hint style="info" %}
**Функція «Texture Aware» на Jetson завжди обробляє по одному зображенню за раз.** Кожному робочому процесу потрібен власний контекст CUDA (~1 ГБ) та власна копія моделі шумозаглушувача, чого не може забезпечити об’єднана пам’ять — тому на Jetson шлях Texture Aware прив’язаний до одного робочого процесу з послідовним доступом до графічного процесора. Очікуйте, що Texture Aware буде помітно повільнішим за Standard на будь-якому Jetson. «Texture Aware» застосовується до зображень Survey3: для знімків LATTICE завжди використовується «Standard» дебейер. Без придатного для роботи CUDA-графічного процесора виконується режим «Standard», і бекенд записує в журнал один рядок `[DEBAYER] … needs a CUDA GPU …` із поясненням причини (показано разом із `chloros-cli --verbose`).
{% endhint %}

## Управління тепловим режимом

Пристрої Jetson мають обмежений тепловий запас, особливо в закритих приміщеннях або під час польотів. Програма Chloros контролює температуру SoC і автоматично регулює розмір пакетів:

| Температура         | Дія                                            |
| ------------------- | ------------------------------------------------- |
| **< 70 °C**          | Нормальна робота — повна швидкість обробки          |
| **70 °C** (Попередження) | Розмір пакета поступово зменшується (від 100 % до 50 % у діапазоні від 70 °C до 80 °C) |
| **80 °C** (Критичний) | Агресивне обмеження (50 % → 0 % у діапазоні від 80 °C до 90 °C) |
| **90 °C** (Вимкнення) | Повне зупинення обробки графічним процесором — необхідне охолодження |

{% hint style="warning" %}
**Забезпечте належну вентиляцію та відведення тепла** для безперебійної роботи, особливо в закритих польових корпусах або бортових системах. Терморегулювання знизить продуктивність обробки даних для захисту апаратного забезпечення.
{% endhint %}

## Управління пам’яттю

Пристрої Jetson використовують **уніфіковану пам’ять** — графічний процесор (GPU) та центральний процесор (CPU) спільно використовують одну й ту саму фізичну оперативну пам’ять (RAM). Зазначений обсяг відеопам’яті (VRAM) (наприклад, ~15,3 ГБ на Orin NX 16 ГБ) не є виділеною пам’яттю для графічного процесора; це та сама оперативна пам’ять, яку використовують операційна система та всі інші процеси.

### Попередження щодо обміну пам’яттю та рекомендації

Перед початком обробки на Jetson командний рядок підраховує кількість RAW-зображень у вашій папці вхідних даних (`.tif`, `.tiff`, `.raw`, `.dng` — попередні перегляди у форматі JPG не враховуються), оцінює піковий обсяг пам’яті, необхідний для виконання, і **попереджає перед запуском**, якщо обсягу оперативної пам’яті та обмінного простору, ймовірно, не вистачить. Попередження має заголовок `LOW MEMORY WARNING - Jetson Detected`, відображає кількість ваших зображень, об’єм оперативної пам’яті, поточний розмір обміну та прогнозований піковий обсяг, а потім видає точні команди `fallocate` / `chmod` / `mkswap` / `swapon`, розмір яких підібрано під вашого проєкту (ніколи менше 8 ГБ). Програма робить паузу на кілька секунд, щоб повідомлення не загубилося у стрічці прокрутки, після чого обробка продовжується.**Оцінки обсягу пам’яті, що використовуються у попередженні:**

| Режим дебейєрингу | Базовий | На зображення |
| --- | --- | --- |
| Стандартний | ~1,5 ГБ | ~10 МБ |
| З урахуванням текстур | ~2,5 ГБ (модель + середовище виконання Python) | ~15 МБ |

Попередження спрацьовує, коли розрахований піковий обсяг перевищує обсяг оперативної пам’яті + обмінну пам’ять за вирахуванням запасу безпеки в 1 ГБ, причому враховується лише **обмінна пам’ять, підкріплена файлами** — конфігурація, що використовує виключно zram, все одно буде позначена як проблема.

Щоб додати обмінну пам'ять вручну (приклад: 8 ГБ):

```bash
# Check current memory and swap
free -h

# Create a swap file
sudo fallocate -l 8G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

# Make persistent across reboots
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### Обробка OOM (Out of Memory)

Під час обробки Chloros відстежує пам'ять графічного процесора (GPU) і плавно знижує продуктивність замість того, щоб аварійно завершувати роботу:

1. Коли завантаження пам’яті графічного процесора перевищує **85%**, розміри пакетів попередньо зменшуються
2. Якщо ситуація нестачі пам’яті все ж виникає, розмір пакета **зменшується вдвічі**, і зменшується ще раз при кожному наступному випадку OOM; кожний наступний успішно оброблений пакет відсуває це обмеження на один крок назад
3. За умов тривалого навантаження конвеєр переходить з `fused_gpu` на енергоефективний маршрут `tiled_gpu`, а в крайньому випадку — на обробку на CPU

Оскільки графічний процесор (GPU) спільно використовує оперативну пам’ять Jetson, обсяг оперативної пам’яті та обмінної пам’яті все ще обмежують час виконання — наведене вище попередження про використання обмінної пам’яті є сигналом, на який слід звернути увагу.

## Впровадження в польових умовах

### Питання енергоспоживання

| Модель Jetson     | Типове енергоспоживання | Примітки                   |
| ---------------- | ------------------ | ----------------------- |
| Jetson Orin Nano | 7–15 Вт              | Роз’єм DC barrel          |
| Jetson Orin NX   | 10–25 Вт             | Роз’єм DC barrel          |
| Jetson AGX Orin  | 15–60 Вт             | USB-C PD або роз’єм DC barrel |

Плануйте енергоспоживання для тривалої обробки — пікове споживання енергії відбувається під час виконання потоку 3 (обробка), що інтенсивно використовує GPU.

### Рекомендації щодо сховищ даних

* **SSD NVMe** настійно рекомендується для розгортань на архітектурі arm64
* SD-карти занадто повільні для обробки — використовуйте їх лише як завантажувальні носії
* Плануйте, що обсяг оброблених даних у 2–3 рази перевищуватиме обсяг вихідних зображень

### Робота без монітора через SSH


Chloros — це ідеальний CLI-інтерфейс для розгортання Jetson без монітора:

```bash
# SSH into the Jetson
ssh user@jetson-hostname

# Process a dataset
chloros-cli process /data/datasets/flight001 --format "TIFF (32-bit, Percent)"

# Monitor export progress
chloros-cli export-status
```

### Постійно активний бекенд для синхронізації часу LATTICE / DAQ-E

Якщо ваш Jetson бездисплейно керує камерами LATTICE або світловими датчиками DAQ-E, увімкніть службу systemd бекенду **від імені вашого користувача**, щоб головний сервер PTP працював безперервно, а скрипти SDK знаходили запущений бекенд (модуль встановлено, але за замовчуванням не ввімкнено):

```bash
sudo systemctl enable --now chloros-backend@$USER.service    # $USER expands to your user name
chloros-cli time-sync status
```

Після цього бекенд працюватиме від вашого імені: записані ним дані належатимуть вам, і він використовуватиме ваш `chloros-cli login`. Детальніше, зокрема про файл root `chloros-backend.service` та про те, як пакет робить порти PTP 319/320 доступними для прив’язки без прав root, див. [Встановлення в Linux](linux-installation.md#always-on-ptp-for-headless-hosts).

### Автоматизована обробка за допомогою systemd

Створіть службу systemd для автоматизованої обробки:

```ini
# /etc/systemd/system/chloros-process.service
[Unit]
Description=Chloros Automated Processing
After=network.target

[Service]
Type=oneshot
User=chloros
ExecStart=/usr/bin/chloros-cli process /data/incoming --output /data/processed
StandardOutput=append:/var/log/chloros-process.log
StandardError=append:/var/log/chloros-process.log

[Install]
WantedBy=multi-user.target
```

`chloros-cli process` завершує роботу з ненульовим кодом, якщо запуск, що запитував продукти, не записує жодних зображень, тому статус помилки systemd є значущим для моніторингу.

Поєднайте з таймером systemd для запланованої обробки:

```ini
# /etc/systemd/system/chloros-process.timer
[Unit]
Description=Run Chloros Processing Every Hour

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable chloros-process.timer
sudo systemctl start chloros-process.timer
```

## Приклади робочих процесів

### Базова обробка на Jetson

```bash
#!/bin/bash
# Process a drone flight dataset on Jetson
chloros-cli process /data/flights/flight_042 \
    --output /data/processed/flight_042 \
    --format "TIFF (32-bit, Percent)" \
    --indices NDVI GNDVI OSAVI
```

### PythonSDK
для Jetson

```python
from chloros_sdk import ChlorosLocal

with ChlorosLocal() as chloros:
    chloros.create_project("field_survey_042")
    chloros.import_images("/data/flights/flight_042")
    chloros.configure(
        indices=["NDVI", "GNDVI", "OSAVI"],
        export_format="TIFF (32-bit, Percent)",
        reflectance_calibration=True
    )
    chloros.process(mode="parallel")

print("Processing complete!")
```

### Пакетна обробка даних з декількох польотів

```bash
#!/bin/bash
# Process all flight datasets in a directory
for flight in /data/flights/*/; do
    name=$(basename "$flight")
    echo "Processing $name..."
    chloros-cli process "$flight" \
        --output "/data/processed/$name" \
        --format "TIFF (32-bit, Percent)" \
        --indices NDVI OSAVI
    echo "Completed $name"
done
```

## Рекомендовані системи Jetson для польового використання

Для польового та повітряного застосування рекомендуємо розглянути такі варіанти несучих плат Jetson Orin NX 16 ГБ:

* **Повітряні/дрони**: Системи з вібростійкістю (MIL-STD), легкі (менше 300 г), з пасивним охолодженням
* **Польові умови з екстремальними навантаженнями**: водонепроникні корпуси класу IP67/IP69K з підключенням камери GigE через PoE
* **Мінімальна конфігурація/економічний варіант**: набори для розробників із додатковими корпусами

Зверніться до [служби підтримки MAPIR](https://www.mapir.camera/community/contact), щоб отримати конкретні рекомендації щодо апаратного забезпечення для вашого сценарію розгортання.
