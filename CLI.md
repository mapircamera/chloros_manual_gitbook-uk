## Що таке CLI


`chloros-cli` — це інтерфейс командного рядка для того самого механізму обробки, який використовує настільна програма Chloros
. Це «тонкий» HTTP
-клієнт, що працює через бекенд Chloros
(локальний сервер на `127.0.0.1:5000`) — більшість команд запускають бекенд автоматично, тому для скрипта достатньо одного виклику `chloros-cli process …`. Після цього сервер продовжує працювати для виконання наступної команди: він зупиняється при виконанні команди `chloros-cli logout` (якщо програма не відкрита або не виконується запуск чи збірка), при виконанні команди `chloros-cli backend stop`, або самостійно через 30 хвилин відсутності клієнта, запуску чи підключеного пристрою. `chloros-cli backend status` відображає це.

Програма працює на **Windows
10/11 (x64)**та**Linux
(x86_64, а також NVIDIA Jetson arm64 на JetPack 6)**, у будь-якому терміналі, без необхідності використання графічного інтерфейсу. Перевірте правильність встановлення за допомогою:

```bash
chloros-cli --version    # prints "Chloros CLI 1.3.0"
```

Короткий огляд сімейств команд:

* **Обробка та обліковий запис** — `process`, `login`, `logout`, `status`, `export-status`, `language` (38 мов — див. [Підтримувані мови](supported-languages.md)), `set-project-folder` / `get-project-folder` / `reset-project-folder`, `selftest`, `update` (лише Linux
/Jetson)
* **Апаратне забезпечення в режимі реального часу** — `lattice` (керування камерою LATTICE, понад 45 підкоманд), `daq pool-*` (датчики освітлення DAQ), `time-sync` (PTP)
* **Автоматизація** — `project` (запуск збереженого проєкту Chloros
у режимі без графічного інтерфейсу, включаючи рецепти збору даних у форматі YAML)

Глобальні параметри, про які варто знати: `--port N` (порт бекенду, за замовчуванням `5000`), `-v/--verbose`, `--restart` (примусовий перезапуск бекенду), `--backend-exe PATH`. Повний перелік див. у [Довіднику CLI
](reference/cli-reference.md).

## Встановлення

CLI
**входить до складу інсталятора Chloros** на всіх платформах — окремого завантаження CLI
немає. Завантажте інсталятор зі сторінки [Завантаження](download.md).

### Windows


Інсталятор розміщує CLI
за адресою:

```

C:\Program Files\Chloros\cli\chloros-cli.exe
```

та одноразово додає цю папку до вашої системи `PATH` (під час оновлення також видаляються дублікати записів, залишені попередніми інсталяторами) — **відкрийте новий термінал**після інсталяції, щоб оновлений `PATH` був виявлений. Інсталятор також розміщує скрипти запуску (`Chloros_CLI.bat` / `Chloros_CLI.ps1`) у кореневій папці інсталяції, а також**Chloros
CLI
** у меню «Пуск», кожен з яких відкриває термінал із готовим до використання `chloros-cli`.

### Linux


Встановіть `.deb` для вашої архітектури за допомогою `apt` (а не `dpkg -i`, який ігнорує рекомендовані вимоги Python
SDK
):

```bash
# Linux x86_64
sudo apt install ./chloros_1.3.0_amd64.deb

# NVIDIA Jetson (arm64, JetPack 6)
sudo apt install ./chloros_1.3.0_arm64_jp6.deb
```

Це встановлює `chloros-cli` до `/usr/bin/chloros-cli` (вже присутні в `PATH`), бекенд та програми CLI
, розпаковані в `/usr/lib/chloros/backend/` та `/usr/lib/chloros/cli/` (`/usr/lib/chloros/chloros-backend` — це запускач, який запускає бекенд), середовище виконання Arena SDK
, необхідне бекенду для камер LATTICE, та Python
SDK
для системи `python3`. Детальніше див. [Встановлення на Linux
](linux/linux-installation.md).

### Перевірка

```bash
chloros-cli --version    # "Chloros CLI 1.3.0"
chloros-cli selftest     # 7-step diagnostic: backend, API, GPU/CUDA, denoiser models
chloros-cli status       # license tier + logged-in user
```

## Вхід та ліцензування

Для доступу до CLI
(та Python
SDK
) потрібен **платний тарифний план Chloros
+**— він доступний у будь-якому платному тарифному плані, але відсутній у безкоштовному. Обмеження застосовується**на стороні сервера** бекендом, а не бінарним файлом CLI
: виклик без входу в систему відхиляється з кодом `401 AUTH_REQUIRED`, а виклик із входом у систему на безкоштовному рівні — з кодом `403 PLAN_UPGRADE_REQUIRED`, незалежно від того, чи надходить він із `chloros-cli`, SDK
чи саморобного HTTP
-клієнта. Оновіть систему за посиланням [https://cloud.mapir.camera/pricing](https://cloud.mapir.camera/pricing).

Увійдіть **один раз з кожної машини**:

```bash
chloros-cli login user@example.com 'YourPassword'
chloros-cli status
```

{% hint style="warning" %}
**Паролі зі спеціальними символами**(`$`, `!`, spaces): wrap the password in**single quotes**, as shown above. In PowerShell double quotes, `$$` спотворюється оболонкою (CLI
виявляє це за кодом 401 і автоматично повторює спробу, але використання одинарних лапок повністю усуває цю проблему).
{% endhint %}

Сесія кешується в `~/.chloros/user_session.json` і продовжує працювати в автономному режимі протягом пільгового періоду тарифного плану (30 днів для місячних тарифів, до закінчення терміну дії для річних). `chloros-cli status` працює навіть без оплаченого тарифного плану, тому причина відмови завжди видна.

{% hint style="danger" %}
**Плануєте запуск безінтерфейсних завдань? Спочатку увійдіть у систему.**Команди запуску бекенду (`process`, `status`, `export-status`, …) без**кешованої сесії**не завершується з помилкою одразу — вона переходить у інтерактивний режим із запрошенням `Email:` / `Password:` на stdin. Тому автоматичне завдання cron або крок CI**зависне в очікуванні введення**. Перед плануванням будь-яких завдань запустіть `chloros-cli login EMAIL 'PASSWORD'` один раз на комп’ютері.
{% endhint %}

## Ваш перший запуск обробки

Вкажіть `process` на папку із записами — програма автоматично виявить Survey3
(`.raw` + `.jpg`), LATTICE (`.tif`/`.tiff`), `.dng` або їх комбінацію:

```bash
chloros-cli process "C:\Images\flight_001"          # Windows
chloros-cli process ~/images/flight_001              # Linux
```

Потоки прогресу передаються в режимі реального часу для кожного потоку конвеєра (виявлення, аналіз, обробка, експорт), а успішне виконання завершується повідомленням про кількість записаних зображень: `Image products written: N`, а потім `(plus M clamp masks)`, якщо під час запуску також були записані [маски обмеження](output-image-formats.md#clamp-masks) (вони не враховуються як продукти).

<!-- SCREENSHOT-NEEDED: terminal capture of a `chloros-cli process` run on a LATTICE captures folder completing successfully — per-thread progress lines visible and the final "Image products written: N (plus M clamp masks)" summary line -->


Якщо бекенд Chloros
вже працює (наприклад, у настільній програмі), `process` використовує його та відкриває в ньому свій проєкт. Він відмовляє, поки програма відкрита на проєкті, який вона сама відкрила: запустіть процес із програми або закрийте цей проєкт. Якщо попередній запуск ще завершується, він чекає на його завершення до 15 секунд, перш ніж відмовити. `--restart` примусово запускає новий бекенд. У Linux
бекенд, який запускається як служба systemd, ніколи не перезапускається: `process` використовує його таким, як є, і там, де в іншому випадку його б перезапустив (`--restart` або імпорт, який нічого не знайшов), він виводить `sudo systemctl restart <unit>` і завершує роботу `1`.

### Куди зберігаються результати

`process` записує результати у **папку проєкту**, а не у вашу папку вхідних даних:

* Якщо `-o` відсутній: проєкт створюється у вашій папці проєктів за замовчуванням (спільній із графічним інтерфейсом; керуйте нею за допомогою `get-project-folder` / `set-project-folder`; якщо нічого не вказано, `Documents/MAPIR/Chloros Projects` у вашій папці користувача), назва якого складається з `-n/--project-name` або мітки часу (`YYYYMMDD_HHMMSS`), якщо це не вказано.
* З `-o PATH`: ця папка **є** папкою проекту. Якщо вона вже містить `project.json`, замість перезапису створюється `_1`/`_2`… замість перезапису. Відносний шлях `PATH` визначається відносно папки, з якої запускається `chloros-cli`.

{% hint style="info" %}
**Відносні шляхи (змінено у версії 1.3.0).** Кожен шлях, який відкриває бекенд — `-o`/`--output` при виконанні будь-якої команди (включно зі стандартним `output` команд запису), `--input`, `--burst-dir`, `--profile`, `--save` та `--mask` — вирішується відносно папки, з якої запускається `chloros-cli`, тому `-o captures/` записує дані у `<current folder>/captures/`. У версії 1.2.0 бекенд розпізнавав їх у власній папці інсталяції, що призводило до помилки «Доступ заборонено». У випадку віддаленого бекенду (`CHLOROS_BACKEND_URL`) шляхи надсилаються у тому вигляді, у якому їх введено, і розпізнаються на цій машині.
{% endhint %}

{% hint style="warning" %}
**Windows
: використовуйте коротку папку проекту, якщо не ввімкнено підтримку довгих шляхів.** Якщо у Windows
вимкнено підтримку довгих шляхів (за замовчуванням у Windows
), жоден шлях до файлу не може перевищувати 260 символів, а продукти розміщуються на рівні, що знаходиться приблизно на 130 символів нижче за папку проекту. `process` перевіряє це перед запуском: занадто глибока папка проекту відхиляється з повідомленням **«Папка проекту занадто глибока для цього комп’ютера»**, пропонується найдовша папка проекту, яка підходить, та інструкція щодо увімкнення довгих шляхів — обробка не відбувається. Використовуйте коротшу папку `-o` (або `set-project-folder`) або увімкніть довгі шляхи Windows
(параметр інсталятора **Увімкнути довгі шляхи Windows**, відмічений за замовчуванням) і перезапустіть Chloros
.
{% endhint %}

Усередині проєкту продукти згруповані **за камерою, а потім за форматом файлу**:

```
<project>/
├── project.json
├── calibration_data.json
└── LATT-M3M-L41-F550/                  # one folder per camera model+lens+filter
    ├── tiff16/
    │   ├── Reflectance_Calibrated_Images/
    │   ├── Debayered_Images/
    │   ├── Preview_Images/
    │   └── NDVI_Index_Images/           # one folder per requested index
    └── tiff32/
        └── Radiance_Images/             # float32 radiance always lands here
```

Папка камери для LATTICE має назву `LATT-<sensor>-<lens>-F<filter>` (відповідає EXIF-даним знімка `Model`), а для Survey3 — `<model>_<filter>` (наприклад, `Survey3N_RGN`) для Survey3
. Папка формату має назву `--format`: `tiff16`, `tiff8`, `png8`, `jpg8` або `tiff32` для `TIFF (32-bit, Percent)`.

Для мультиспектральної камери M3C у папці формату, поряд із папками продуктів, також може з’явитися папка `clamp_masks/` (наприклад, `tiff16/clamp_masks/Reflectance_Calibrated_Images/` та `tiff32/clamp_masks/Radiance_Images/`). У ній зберігаються маски для кожного пікселя продуктів випромінювання та відбиття, в яких під час розкладання смуг негативні значення були обмежені до нуля — див. [Маски обмеження](output-image-formats.md#clamp-masks). Жодна папка з продуктами ніколи не містить масок.

{% hint style="info" %}
**Кожен експортований продукт зберігає ім’я файлу-джерела.**Експорт яскравості з `capture_..._raw.tif` все ще має назву `capture_..._raw.tif` — просто він знаходиться в `tiff32/Radiance_Images/`.**Папка ідентифікує продукт, а не ім’я файлу**, тому використовуйте глобальні символи для пошуку каталогу, а не для суфікса `*radiance*`.
{% endhint %}

### Параметри, які ви насправді використовуватимете

| Параметр | За замовчуванням | Що він робить |
| --- | --- | --- |
| `-o, --output PATH` | папка проекту за замовчуванням | Розташування папки проекту (див. вище). |
| `-n, --project-name NAME` | мітка часу | Назва проєкту. |
| `--format FMT` | `TIFF (16-bit)` | Одне з `TIFF (16-bit)`, `TIFF (8-bit)`, `TIFF (32-bit, Percent)`, `PNG (8-bit)`, `JPG (8-bit)`. Chloros
не збільшує роздільну здатність: на всіх 8-бітних зображеннях формат з більшою глибиною записується як `TIFF (8-bit)`, і про це зазначається лише один раз. |
| `--indices NAME [NAME ...]` | немає | Індекси рослинності для експорту (див. [Індекси рослинності](#vegetation-indices)). |
| `--debayer {standard,texture-aware}` | `standard` | `texture-aware` = нейронне дебейєрування, повільніше, найвища якість (Chloros
+, потребує графічного процесора з підтримкою CUDA: без нього використовується `standard`; не застосовується до знімків LATTICE, для яких завжди використовується `standard`). |
| `--vignette / --no-vignette` | увімкнено | Корекція віньєтування. |
| `--reflectance / --no-reflectance` | увімкнено | Калібрування відбиття; для LATTICE це також перемикач продукту відбиття. |
| `--input-level {auto,raw,debayered,processed}` | `auto` | Примусове встановлення точки входу в конвеєр для TIFF-файлів LATTICE. |

Щодо всього іншого — налаштування виявлення цілей, PPK, фіксаторів експозиції, прапорців вирівнювання масивів — див. [розділ `process` у довіднику CLI
](reference/cli-reference.md).

## Вибір даних для експорту (продукти LATTICE)

Обробка LATTICE розподіляється на **усі відповідні продукти за один прохід**. Чотири перемикачі для кожного продукту**за замовчуванням увімкнені**; скористайтеся формою `--no-`, щоб вимкнути один із них:

| Перемикач | Продукт |
| --- | --- |
| `--debayered` | Лінійна демозаїка → `Debayered_Images/`: видалено темне зміщення калібрувального набору, потім виконано демозаїкування з урахуванням країв, без корекції лінійності, вирівнювання поля або розкладання — той самий файл, який зберігається під час зйомки на рівні `debayered`. Зберігається в природній орієнтації сенсора (записано в XMP). |
| `--preview` | Попередній перегляд на екрані (баланс білого + гамма; розтягнення у фальшивих кольорах для мультиспектральних знімків) → `Preview_Images/` |
| `--radiance` | float32 — інтенсивність випромінювання, Вт/м²/ср/нм → `Radiance_Images/` (завжди `tiff32/`) |
| `--reflectance` | uint16 коефіцієнт відбиття, сумісний з Pix4D → `Reflectance_Calibrated_Images/` |

Камери RGB
-типу завжди випромінюють лише дані після дебейєрингу + попередній перегляд — інтенсивність випромінювання/відбиття для окремих діапазонів не має значення для широкосмугового датчика, тому ці перемикачі для них не діють. Survey3
`.raw` ігнорує ці перемикачі та дотримується стандартного шляху відбиття/цільового шляху.

```bash
# Radiance only — no DAQ downwelling needed
chloros-cli process ~/captures/lattice_flight --no-debayered --no-preview --no-reflectance
```

**`--reflectance-source {auto,target,daq}`** (за замовчуванням `auto`) вибирає еталон відбиття: `auto` робить [калібрувальну мітку](calibration-targets.md), що пройшла контроль якості (QA), в межах кадру абсолютним еталоном і, за відсутності мітки, використовує коефіцієнт поділу світлового датчика DAQ (ρ = π·L/E), якщо мішень відсутня (мішень, що пройшла контроль якості з прапорцем, конкурує з DAQ за виміряним показником); `target` діє строго (без заміни даними DAQ); `daq` є авторитетним для DAQ. Скани мішеней, виміряні за одиницею, можна надати за допомогою `--target-reflectance-dir`.

{% hint style="info" %}
**Зчитування пікселів відбиття:**значення DN, що відповідає ρ = 1,0, є**для кожного джерела** — файли LATTICE вставляють тег `Chloros:PixelScale=32768` у XMP; файли Survey3
використовують значення 65535 і не містять тегу `Chloros:PixelScale` (вони містять інші теги обробки `Chloros:*`). Зчитуйте тег і діліть на його значення, а не припускайте, що воно є постійним. Деталі та один навмисний крайній випадок без масштабу наведено в [Довіднику CLI
](reference/cli-reference.md).
{% endhint %}

**Обробка завжди починається з `raw`.** Похідні продукти (експортовані дані після дебейєрингу, випромінювання та відбиття) ніколи не повертаються назад у конвеєр — їх повторне імпортування та обробка призвели б до подвійного застосування математичних формул калібрування, тому Chloros
пропускає їх і повідомляє про це. `--input-level` — це спеціально передбачений «запасний вихід» на випадок, коли вам дійсно потрібно примусово задати точку входу.

## Коли запуск завершується з помилкою

Починаючи з версії 1.2.0, `process` видає явне повідомлення про збій замість того, щоб «успішно завершитися» без будь-яких результатів:

* Запуск, який **запитував продукти, але не записав жодного**— лише `project.json` та `calibration_data.json` — виводить `Processing finished but wrote no image products.` і**завершується з ненульовим результатом**, тож скрипти можуть це виявити. Типові причини: вхідна папка не була розпізнана як знімок (перевірте структуру та `--input-level`), або кожен запитуваний продукт був непридатним для цих камер (наприклад, запит на радіанс/відбиття від камер, що підтримують лише RGB
).
* **Навмисний запуск лише для метаданих** (усі продукти вимкнені, без `--indices`) все одно вважається успішним — порожній вихідний файл зображення в цьому випадку є правильним результатом.
* Запустіть процес знову з параметром `--verbose` і перевірте журнал бекенду на наявність рядків `[LATTICE-EXPORT]` / `[EXPORT-CHECK]`, які пояснюють пропуски для окремих камер.
* У Windows
, де вимкнено підтримку довгих шляхів, папка проєкту, яка занадто глибоко вкладена і перевищує обмеження шляху в 260 символів, відхиляється **до** початку обробки, при цьому використовується найдовша папка проєкту, яка вміщується (див. [Куди зберігаються вихідні файли](#where-the-outputs-land)).
* Команди запису (`lattice capture`, `lattice array-capture` та інші сімейства команд запису) вказують імена всіх файлів, які не вдалося записати, і завершують роботу з кодом `1`; повторні записи зупиняються, коли диск заповнений.

Коди завершення: `0` — успіх · `1` — загальна помилка · `2` — помилка аргументу · `130` — перервано за допомогою Ctrl+C.

## Індекси рослинності

Запустіть `--indices` із одним або кількома іменами пресетів; кожен індекс зберігається у власній папці `<INDEX>_Index_Images/`:

```bash
chloros-cli process ~/images/flight_001 --indices NDVI GNDVI OSAVI
```

22 попередньо задані імена, які `process --indices` приймає:

`NDVI` `GNDVI` `NDRE` `OSAVI` `SAVI` `MSAVI2` `EVI` `MSR` `TDVI` `LAI` `GCI` `GRVI` `GSAVI` `GOSAVI` `NLI` `MNLI` `RDVI` `WDRVI` `CVI` `ENDVI` `GLI` `VARI`

До проекту додається ім’я, якого в ньому ще немає. Ім’я, яке не є попередньо заданим або яке не можна утворити за допомогою діапазонів камер, пропускається з попередженням, у якому вказується це ім’я. Якщо CLI
не може прочитати поточний список індексів проєкту, він залишає список без змін і видає попередження, замість того щоб замінити його.

{% hint style="warning" %}
**Існує три списки індексів — не плутайте їх.**У випадаючому меню «Налаштування проєкту» графічного інтерфейсу є 27 формул (додає `FCI1`, `FCI2`, `GARI`, `GEMI`, `LCI` — ці п’ять доступні лише в графічному інтерфейсі та**не** діють для `--indices`). Команда `lattice index --preset` для роботи в режимі реального часу/офлайн використовує власний окремий список із 22 пресетами. Формули та математичні обчислення для діапазонів описані в розділі [Формули мультиспектральних індексів](project-settings/multispectral-index-formulas.md).
{% endhint %}

## Датчики освітленості DAQ: короткий огляд

Сімейство `daq pool-*` керує спектральними датчиками DAQ від MAPIR
(DAQ-U через USB, DAQ-M через BLE, DAQ-E через Ethernet) через постійний пул бекенду — графічний інтерфейс (GUI), інтерфейс командного рядка (CLI
) та набір інструментів розробника (SDK
) використовують один спільний дескриптор у режимі реального часу. **`pool-*` — це підтримуваний шлях DAQ у поставленому CLI
**; інші підкоманди `daq`, на які ви можете натрапити, є лише внутрішнім інтерфейсом MAPIR
, призначеним лише для джерел даних, і завершують роботу з явною помилкою, що вказує на `pool-*`.

```bash
# 1. Open a pooled session (pick the line matching your sensor)
chloros-cli daq pool-connect                              # smart-detect
chloros-cli daq pool-connect --port COM3                  # DAQ-U on a specific COM port
chloros-cli daq pool-connect --mac AA:BB:CC:DD:EE:FF      # DAQ-M by BLE MAC
chloros-cli daq pool-connect --eth-host daq-e-xxx.local   # DAQ-E by hostname (reliable)

# 2. List pooled sensors and their ids
#    (DAQ-U ids look like 'CB-7C-A8-2E-5F'; DAQ-E ids like 'daq-e-def330')
chloros-cli daq pool-list

# 3. Read the latest calibrated spectrum (W/m²/nm)
chloros-cli daq pool-latest --sensor-id CB-7C-A8-2E-5F

# 4. Record a calibrated .daq file for 60 s
chloros-cli daq pool-record --sensor-id CB-7C-A8-2E-5F --duration 60 \
  -o ~/Documents/spectra --device-name "field-A"

# 5. Release
chloros-cli daq pool-disconnect --sensor-id CB-7C-A8-2E-5F
```

`pool-record` без `--duration` працює до `pool-record --stop`; каталог виводу за замовчуванням — `~/Documents/DAQ Live View/` **на машині бекенду**. Профіль корекції конденсатора вибирається під час підключення (`--cap-id`, за замовчуванням на сервері — `sunshine_cosine`) і може бути замінений у режимі реального часу за допомогою `pool-set-cap` — профілі обмеження та відкалібрований діапазон датчика описані в розділах про DAQ цього посібника.

{% hint style="warning" %}
**DAQ-E на хості з кількома мережевими картами:** перше автоматичне виявлення `pool-connect --eth` після завантаження може завершитися невдачею навіть за умови справності датчика. `--eth-host <ip-or-hostname>` є надійнішим варіантом — використовуйте його, коли виявлення не дає результатів.
{% endhint %}

## Камери LATTICE, PTP та автоматизація проектів

Сімейство `lattice` (понад 45 підкоманд) охоплює повний цикл роботи з камерами LATTICE: виявлення, окремі знімки, постійні синхронізовані масиви з використанням потоку підключення Smart-Prep у графічному інтерфейсі, попередній перегляд у браузері в режимі реального часу, вирівнювання, обчислення індексів та діагностика мережевих карт хоста. Приклад:

```bash
chloros-cli lattice info                                          # discover cameras
chloros-cli lattice capture -o output/                            # one frame, all export types
chloros-cli lattice array-connect --serials SN1,SN2,SN3,SN4       # persistent synced array
chloros-cli lattice array-capture --processing reflectance -o out/
```

Поряд із цим: `chloros-cli time-sync` надає звіт про головний сервер PTP, який працює на хості Chloros
(камери LATTICE та датчики DAQ-E підпорядковуються йому для синхронізації часових міток між пристроями), а `chloros-cli project` відкриває збережений проєкт Chloros
та керує його камерами, масивами та датчиками у бездисплейному режимі — включаючи скриптові рецепти збору даних у форматі YAML.

Ці три сімейства (`lattice`, `project`, `daq pool-*`) також є єдиними, які підтримують `CHLOROS_BACKEND_URL` для керування **віддаленим** бекендом; основні команди завжди спрямовані на локальну машину.

Повні покрокові інструкції наведені в розділах, присвячених LATTICE, цього посібника; опис кожного прапора міститься в [Довіднику CLI
](reference/cli-reference.md).

## Усунення несправностей: 5 найпоширеніших випадків

| Симптом | Виправлення |
| --- | --- |
| `Login required` або заплановане завдання зависає на запрошенні `Email:` | Один раз запустіть `chloros-cli login EMAIL 'PASSWORD'` на цій машині — команди без кешованої сесії будуть виконуватися в інтерактивному режимі, а не завершуватимуться з помилкою. |
| `backend unreachable` | Запустіть настільну програму Chloros
або запустіть серверну частину самостійно: `"C:\Program Files\Chloros\backend\chloros-backend.exe"` у Windows
(папка `backend` у вашій папці інсталяції; її немає в `PATH`), `chloros-backend` у Linux
. `chloros-cli backend status` показує, чи працює якийсь із них; `lattice`/`project`/`daq pool-*` ніколи не запускають його. Якщо ви налаштовуєте їх на віддалений бекенд, перевірте `CHLOROS_BACKEND_URL`. |
| Блокування підключення масиву: `FRAMES WILL DROP` / `Reduce ROI to enable` | Скидання кільця прийому мережевої карти хоста до значень за замовчуванням — головна причина відмови раніше працюючої системи від підключення, зазвичай після оновлення драйвера мережевої карти. Запустіть `chloros-cli lattice network --fix` із терміналу з **підвищеними** правами (або встановіть `ReceiveBufferLen=256`, `PendingReceives=64`); див. розділ *Налаштування та оптимізація мережевої карти хоста* у довіднику. |
| Підкоманда `daq` завершує роботу: «потрібен повний пакет daq…» | Використовуйте команди `daq pool-*`, які керують тим самим датчиком через бекенд: підключення, потокова передача, запис, вибір капсули, а для DAQ-E — його мережеві налаштування, перезапуск та оновлення прошивки (або `chloros_sdk.connect_daq_sensor()` з Python
). |
| Jetson виводить попередження про використання підкачки перед обробкою великих папок | Додайте підкачку на базі файлів — CLI
виведе точні команди `fallocate`/`swapon`, які потрібно виконати. |
