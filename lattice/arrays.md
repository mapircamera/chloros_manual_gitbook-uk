# Масиви з декількох камер

**Масив**LATTICE — це дві або більше камер LATTICE, з&#x27;єднаних в один синхронізований блок. Одна з камер є**головним пристроєм**: вона подає апаратний імпульс тригера GPIO на спільну лінію синхронізації (за замовчуванням**Line2**), завдяки чому всі камери фіксують один і той самий момент. Chloros додає синхронізацію часу за протоколом PTP, попередній перегляд у реальному часі (кадри з кожної камери окремо або єдиний вирівняний багатосмуговий композитний знімок), а також синхронізовану зйомку — кожен цикл зйомки створює одну**групу кадрів**, у якій усі камери мають однаковий часовий штамп та ідентифікатор кадру (відображається як `fid:N` у вихідних даних зйомки).

Масиви — це спосіб, за допомогою якого монохромні (M3M) камери створюють індекси рослинності — одна камера надає один діапазон, а масив вирівнює їх у багатодіапазонний стек. Див. [Монохромні камери та індекси рослинності](mono-indices.md).

Існує три рівнозначні способи підключення масиву, і всі вони запускають один і той самий потік «smart-prep»:

| Поверхня | Точка входу |
| --- | --- |
| Графічний інтерфейс | Вкладка «Камери» → **Підключити масив** (синя кнопка) |
| CLI | `chloros-cli lattice array-connect --serials SN1,SN2,…` (перший серійний номер = головний) |
| Python SDK | `connect_array(serials=[…])` → `ArraySession` (перший серійний номер = головний) |

Smart-prep виконує, у такому порядку: перевірку мережевих можливостей (ICMP DF ping + GVSP-перевірка), вибір рівня синхронізації, автоматичне зменшення розміру кадру для адаптації до пропускної здатності каналу, увімкнення PTP, автоматичний вибір формату пікселів для кожної камери, початкові налаштування автоматичної експозиції на основі збереженого стану кожної камери та налаштування тригера GPIO на лінії 2.

{% hint style="info" %}
Камери мають бути доступними по каналу зв’язку, перш ніж будь-яка з цих функцій запрацює — див. розділ [Підключення камер](connecting.md) щодо виявлення, адресації та завантаження калібрувальних даних під час першого підключення. Для систем із декількома камерами налаштування кільця прийому мережевої карти хоста мають таке ж значення, як і швидкість каналу зв’язку; повна таблиця «симптом→виправлення» наведена в розділі [CLI Довідка § Налаштування та оптимізація мережевої карти хоста](../reference/cli-reference.md#host-nic-setup--tuning-lattice-arrays).
{% endhint %}

## Діалогове вікно «Підключення масиву»

Вкладка «Камери» → **«Підключити масив»**відкриває майстер із трьох кроків:**Вибір → Режим відображення → Налаштування**.

### Крок 1 — Вибір головного пристрою та підлеглих

<!-- SCREENSHOT-NEEDED: Array Connect dialog, Select scene, with 3-4 LATTICE cameras discovered. Table showing Camera / Serial / IP / Master radio / Slave checkbox columns, with the green "GPIO master detected — selections pre-populated" probe banner visible above the table. -->

Привід відкриття діалогового вікна мережа сканується («Сканування мережі...»), після чого перевіряється підключення тригера GPIO («Перевірка підключення GPIO...»). Для формування масиву потрібно щонайменше **2 камери**.

Перевірка підключення за можливості попередньо заповнює поля вибору ролей і відображає один із трьох банерів:

| Банер | Значення |
| --- | --- |
| «Виявлено головну камеру GPIO — поля вибору попередньо заповнено» (зелений) | Перевірка виявила топологію тригера; прапорці «головний» та «підлеглий» вже встановлені. |
| «Головний пристрій не виявлено — перевірте кабель GPIO» (помаранчевий) | Жодна камера не зафіксувала імпульс тригера; перевірте кабельне з’єднання синхронізації. Ви все ще можете вибрати ролі вручну. |
| «Відсутній кабель синхронізації: {серійні номери}» (помаранчевий) | До перелічених камер не підключено кабель синхронізації. |

Таблиця камер містить стовпці **Камера / Серійний номер / IP / Головна (радіо) / Підлегла (поле вибору)**:

* Виберіть саме **одну головну**та**одну або кілька підлеглих**. Повторне натискання на радіопозначку поточного майстра знімає її.
* Камеру з позначкою **«Відсутній кабель синхронізації»** неможливо вибрати як ведений пристрій — ведений пристрій без підключення тригера буде вічно чекати на лінії синхронізації та передаватиме непрацююче зображення. Замість цього підключіть цю камеру як автономну.
* Камери, які вже підключені в автономному режимі, *не* вимикаються: підключення до масиву звільняє автономну сесію та знову відкриває камеру всередині масиву.

**Далі: Режим відображення →**стає доступним після вибору головного пристрою та принаймні одного підлеглого.**Повторне сканування** запускає процес виявлення та перевірку підключення заново.

{% hint style="warning" %}
**Скасувати** недоступно під час сканування або перевірки — скасування в процесі перевірки може призвести до збою камери SDK на прошивці камери LATTICE. Дочекайтеся завершення обертання індикатора.
{% endhint %}

### Крок 3 — Налаштування масиву та прогнозований результат

<!-- SCREENSHOT-NEEDED: Array Connect dialog, Settings scene, healthy state: left column with ROI / Binning / Pin resolution / Trigger Rate controls, right "Projected Outcome" column showing green "Simultaneous capture" tier, an fps range, the NIC line, the "Sim-emit burst" line, and the "Wire budget" line with a checkmark. -->

При вході в цю сцену Chloros запитує у сервера **рекомендацію**і автоматично застосовує комбінацію ROI та бінінгу, яка відповідає приймальному кільцю вашої мережевої карти (програма віддає перевагу бінінгу над обрізанням ROI, оскільки бінінг зберігає повне поле зору). Кожна зміна, яку ви вносите, запускає аналіз у режимі реального часу та оновлює праву панель**Прогнозований результат**.

Ліва колонка — налаштування:

| Елемент керування | Варіанти | За замовчуванням | Примітки |
| --- | --- | --- | --- |
| **ROI (поле зору)** | Повне (2048×1536) / Половина (1024×768) / Чверть (512×384) | Повне | Обрізка датчика: обрізка до половини/чверті до меншої області з рідним кроком пікселів. |
| **Біннінг** | 1× / 2× (сума 2×2) / 4× (сума 4×4) | 1× | Апаратний біннінг: 2×2 = повне поле зору при чверті витрат на передачу даних; 4×4 = повне поле зору при 1/16. Приховано, якщо камери не підтримують бінінг. |
| **Зображення на лінії передачі** (зчитування) | — | — | Ширина × висота після бінінгу, що фактично передається по лінії, округлена до кратних 16 (мінімум 64). |
| **Роздільна здатність виводів**| прапорець | вимкнено | Chloros зазвичай автоматично збільшує бінінг під час підключення, коли прогнозована частота падає нижче**1,5 кадрів за секунду**. Фіксація зберігає обраний розмір кадру та приймає нижчу швидкість — і перетворює конфігурацію з перевищенням пропускної здатності на категоричну відмову у з’єднанні замість автоматичного зниження швидкості. |
| **Частота спрацьовування** | 0,5–60 кадрів/с, крок 0,1 | порожнє = авто | Частота спрацьовування тригера головного пристрою. Залиште поле порожнім, щоб Chloros визначив його самостійно. |
| **Бюджет каналу**| 20–2000 МБ/с, крок 10 | порожнє = авто | Скільки хост може фактично прийняти, у МБ/с —**єдине число, від якого залежить весь розподіл масиву.** Визначається автоматично за даними мережевого адаптера. Зменште це значення, якщо масив повідомляє про пошкоджені кадри: виявлене значення завищує можливості USB-адаптерів та спільних комутаторів. Зміна цього параметра призводить до повторного запуску прогнозування в режимі реального часу. |

Правий стовпець — **Прогнозований результат**:

* **Рівень синхронізації** — «Одночасний запис» (зелений), «Одночасний запис (поетапна передача FTD)» (зелений), «Поетапний запис (зсув 100 мс)» (бурштиновий) або «Конфігурація занадто велика» (червоний).
* **Прогноз кадрів за секунду** — відображається у вигляді діапазону («тьмяний → яскравий»), оскільки частота синхронізованого масиву обмежується витримкою найповільнішої камери.
* **Рядок мережевої карти** — швидкість з’єднання та стабільна пропускна здатність («NIC {mbps} Мбіт/с · стабільна {N} МБ/с»).
* **Перевірка пакетів із симульованим одночасним випромінюванням** — чи може кільцевий приймач мережевої карти хоста прийняти один одночасний пакет від усіх камер («Пакет із симульованим одночасним випромінюванням: X МБ · доступна ємність кільцевого приймача мережевої карти: Y МБ ✓/✗»).
* **Перевірка пропускної здатності каналу** — сукупний попит у стаціонарному режимі порівняно з безпечною для уникнення колізій граничною пропускною здатністю каналу («Пропускна здатність каналу: {попит} МБ/с, що вимагається {n} камерами · гранична пропускна здатність {ceiling} МБ/с ✓/✗ перевищення пропускної здатності»).
* **«Максимальна кількість камер на цьому каналі: {n} — встановлюється нижньою межею пропускної здатності на камеру, тому об’єднання не збільшує її»** — відображається, коли ви наближаєтеся до (або перевищуєте) граничну кількість камер.
* **«З такими налаштуваннями КАДРИ БУДУТЬ ВТРАЧАТИСЯ».**— червоне попередження з поясненням причини з боку серверної частини, а також списком перешкод і синіми**пропозиціями щодо виправлення** («Щоб вмістити цей масив у мережу» / «Щоб розблокувати одночасне знімання»).

Кнопка **«Застосувати та підключити»** недоступна, доки не з’явиться прогноз, а її напис пояснює, чому відбувається відмова:

| Напис на кнопці | Значення | Що насправді допомагає |
| --- | --- | --- |
| «Аналізується...» | Аналіз ще триває. | Зачекайте. |
| **«Занадто багато камер для цієї мережі»**| Масив перевантажує канал (провал перевірки сумарного навантаження). | Менше камер, використання джамбо-фреймів на всьому шляху або швидша мережева карта.**Зменшення ROI НЕ допоможе** — див. нижче. |
| **«Зменшіть ROI, щоб увімкнути»** | При таких налаштуваннях кадри будуть втрачатися (провал перевірки пакетів та кільцевої структури). | Зменшіть ROI, збільште бінінг або виправте кільце прийому мережевої карти. |

Під час підключення може з’явитися зелена **панель завантаження калібрування** із індикатором прогресу для кожного послідовного порту: коли камера підключається до комп’ютера вперше, Chloros завантажує з камери через GigE заводський пакет калібрування розміром приблизно 3,8 МБ (приблизно 70 секунд на камеру). Камери, що знаходяться в кеші, ніколи не показують цю панель. Див. [Підключення камер](connecting.md).

## Пропускна здатність: скільки камер можна підключити

Кількість камер, яку може підтримувати масив, залежить від пропускної здатності кабелю, а не від Chloros, тому розрахункові дані наведені в посібнику з обладнання: **[Планування пропускної здатності масиву](https://mapir.gitbook.io/lattice-camera/setup/array-bandwidth-planning)**.

Що з ними робить Chloros: діалогове вікно підключення запускає мережевий тест, прогнозує досяжну частоту кадрів і вибирає відповідний рівень. Якщо масив перевантажує канал, він відмовляється від підключення, а не пропускає пакети без повідомлення — див. панель прогнозованих результатів, описану вище.

## Коли кадри губляться

Камера може бути відсутньою в опублікованій групі з двох абсолютно різних причин,
і вони потребують протилежних способів усунення. Chloros підраховує їх окремо, а не повідомляє одне
«неповне» число, яке не вказує на жодну з них:

| Що сталося | Що це означає | Де шукати |
| --- | --- | --- |
| **Пошкоджений**— кадр надійшов, але мав структурні пошкодження | Втрата пакетів GVSP на мережевому шляху |**Пропускна здатність каналу**, кільце прийому мережевої карти, джамбо-кадри, комутатор |
| **Ніколи не надійшов**— кадр взагалі не надійшов | Камера не спрацювала або з неї нічого не вийшло |**Кабель синхронізації M8**, лінія синхронізації, чи всі учасники системи увімкнені |

Розподіл переоцінюється кожні 10 секунд під час передачі потоку масиву. Якщо показник перевищує 5 %, це
реєструється із зазначенням обох значень, а про кожен пошкоджений буфер повідомляється при першому
випадку для кожної камери, після чого дані підсумовуються щохвилини, щоб довгі сесії залишалися читабельними.

**Пошкоджені кадри з нульовим показником «ніколи не надійшли» означають, що спрацьовування та синхронізація кабелю працюють ідеально**, а кожен втрачений кадр знаходиться на мережевому шляху. Вирішити проблему можна, зменшивши**Wire Budget** та
перепідключившись.

{% hint style="warning" %}
**Зменшення частоти спрацьовування не допомагає усунути пошкоджені кадри.** Пакети камери
записуються одноразово під час підключення. Зниження частоти спрацьовування змінює частоту виникнення пакетних
потоків, а не швидкість, з якою сам пакетний потік передається по кабелю. На виміряній установці з 4 камерами
5-кратне зниження частоти спрацьовування нічого не змінило, тоді як зменшення «бюджету каналу» з 240 до
200 МБ/с дозволило знизити рівень пошкоджених кадрів у цій же системі з 10,4 % до нуля.
{% endhint %}

Масив, що працює, не може самостійно перепланувати свою роботу — від’єднайтеся та під’єднайтеся знову, щоб вибірник часу з’єднання
міг працювати з урахуванням нового ліміту пропускної здатності.

### Мережеві адаптери USB обмежені швидкістю 200 МБ/с

USB-адаптер Ethernet заявляє про свою швидкість *Ethernet*-з&#x27;єднання, але те, що він насправді
може підтримувати, обмежується шиною USB та її драйвером. Раніше USB-ключу 10GbE приписували
пропускну здатність приблизно 1000 МБ/с — значення, яке ніхто ніколи не вимірював, — і при синхронізації
чотирьох камер з цією уявною резервною потужністю пошкоджувалося 6–18 % кадрів, хоча масив
продовжував показувати нормальну цільову частоту кадрів. Зараз пропускна здатність адаптерів, підключених через USB, обмежена
**200 МБ/с**. Це абсолютне значення, а не відсоток, оскільки обмеженням є сама
шина: адаптер USB 1 Гб/с забезпечує приблизно 80 МБ/с і не підпадає під це обмеження.

Якщо ваш хост-комп’ютер справді працює швидше, ніж це обмеження, збільште **Wire Budget**, щоб це відобразити.

## Синхронізація часу PTP

*Синхронізація* кадрів здійснюється за допомогою апаратного тригера; **PTP** (IEEE 1588 PTPv2) забезпечує однакові *мітки часу* на всіх пристроях. Ця функція вмикається за замовчуванням під час підключення масиву:

* **Хост-бекенд Chloros виконує роль головного сервера PTP**. Камери LATTICE та світлові датчики DAQ-E працюють у режимі підлеглих пристроїв у домені 0, тому часові мітки зображень та спектри DAQ збігаються за одним тактом (~1 мс).
* `--no-ptp` (CLI) вимикає його для роботи на стенді — у цьому випадку мітки часу між камерами **не** є порівнянними.
* Перевірте стан синхронізації за допомогою CLI:

```bash
chloros-cli time-sync status     # grandmaster state, clock identity
chloros-cli time-sync peers      # slaves seen (cameras + DAQ-E sensors)
chloros-cli time-sync cameras    # per-camera PtpStatus / PtpOffsetFromMaster / PtpMeanPathDelay
```

На самій вкладці «Камери» немає індикатора PTP; параметри синхронізації для кожної камери, що відображаються там, — це доступні лише для читання **Роль**(Майстер/Підлеглий),**лінія синхронізації** та рівень можливостей масиву. Стан PTP DAQ-E відображається у деталях датчика на вкладці «Світлові датчики».

## Вигляд

<!-- SCREENSHOT-NEEDED: Cameras tab with a connected combined array: sidebar showing the ARRAY row (color badge, array name, "DAQ · on" pill) with indented member camera rows, and the main area showing the combined index composite tile with the LUT-colored NDVI render, top-left array name pill, and top-right fps readout. -->

масиву в режимі реального часу Головна область відображення пропонує два макети (перемикання у верхній панелі): **вигляд у вигляді сітки**(кожна плитка є коміркою; перетягуванням можна змінювати порядок, коли замок сітки розблоковано) та**вигляд у вигляді списку**(масиви на всю ширину зверху, одна активна камера нижче). Повзунок**Масштаб стрічки** регулює розмір плиток; якщо ширина комірки менше 200 пікселів, накладки з назвою та частотою кадрів автоматично приховуються.**Окремий режим** показує одну плитку на кожну камеру. На кожній плитці відображаються:

* назва камери (у верхньому лівому куті),
* **показник частоти кадрів** (у верхньому правому куті) — це *фактична частота зйомки* камери, що повідомляється серверною частиною, а не частота оновлення попереднього перегляду (попередній перегляд у реальному часі обмежений 30 кадрами на секунду незалежно від частоти зйомки),
* індикатор стану — зелений (трансляція) / жовтий (завантаження) / червоний (помилка),
* **індикатор застарілого кадру**, якщо протягом 2 с не надійшов свіжий кадр — це нормально протягом ~5 с після будь-якого підключення/відключення, поки серверний модуль перерозподіляє пропускну здатність між камерами.**Комбінований режим**відображає єдину композитну плитку: сервер виконує дебейерінг, масштабування, вирівнювання, шумозаглушення, перетворює у випромінювання за кожною смугою (плюс коефіцієнт відбиття DLS, якщо підключено датчик освітлення), обчислює індексний вираз масиву, застосовує LUT і передає результат у форматі MJPEG. Доки не буде відтворено перший вирівняний кадр, плитка відображає свій стан: «Підготовка масиву…», «Калібрування вирівнювання…», «Очікування першого кадру…», або — якщо ліміт спроб автоматичного вирівнювання (~30 с) вичерпано — «Потрібне вирівнювання» з кнопкою**«Калібрувати вирівнювання»**.

Корисні факти про комбінований режим:

* Композит прив’язаний до кадру **головної**камери. Наведення AE-ROI та точковий замір експозиції на композиті є точними для головної камери та наближеними для підлеглих; використовуйте**Розділений вигляд** (налаштування масиву → «Показати камери-учасниці») для отримання плиток з точністю до пікселя для кожної камери без відкриття додаткових з’єднань з камерами.
* **Display Layers**(налаштування масиву; за замовчуванням вимкнено) дозволяє вибрати передній і задній шари — будь-яку камеру-учасницю або**Index**. Якщо передній шар = Index, пікселі за межами мінімального/максимального значень LUT відображають задній шар.
* **Роздільна здатність рендерингу** (за замовчуванням 720p) встановлює висоту потокового відео *та* розмір збереженого композитного файлу для експорту. Зображення з кожної камери завжди експортуються у повній роздільній здатності.
* Вирівнювання обчислюється для кожної сесії та ніколи не зберігається — див. розділ «Вирівнювання» на панелі налаштувань масиву, де наведено залишкові значення RMS та кнопку «Перекалібрувати».

## Запис: моніторинг проти аналізу

Поверхні запису масиву чітко поділяються на **рівень моніторингу**(запис того, що ви бачите) та**рівень аналізу** (запис необроблених даних, калібрування пізніше):

| Робочий процес | Рівень | Що зберігається | Графічний інтерфейс | CLI |
| --- | --- | --- | --- | --- |
| **Зйомка**(фотографії) | Аналіз | Одна синхронізована група кадрів за кожен прохід; файли для кожної камери на кожному вибраному рівні експорту (сирі/без дебейєрингу/радіанс/відбиваність/попередній перегляд/індекс) + `.daq` файли sidecar | Кнопка**Зберегти все** + Налаштування зйомки | `lattice array-capture` |
| **Запис індексного відео** | Моніторинг | Композитний індекс у реальному часі, як відображається на екрані — 8-бітний, роздільна здатність попереднього перегляду, вбудована LUT; потребує відкритого потоку в реальному часі | ● Запис індексного відео (об’єднані масиви) | `lattice array-record` |
| **Необроблений потік кадрів → створення відео**| Аналіз | Необроблені кадри з датчика з повною частотою зчитування + маніфест + `.daq`, потім офлайн-реконструкція у відкаліброване відео з індексом яскравості / відбиття, синхронізоване за часом із показаннями DAQ | ⦿ Запис необробленого потоку кадрів →**Створення відео** | `lattice array-burst` → `lattice array-build-video` |

Практичне правило: якщо пікселі будуть надавати *вимірювальні дані*, використовуйте режим захоплення або серійної зйомки (для аналізу); якщо вам просто потрібно *переглянути або продемонструвати* те, що бачила матриця, записуйте індексове відео (для моніторингу).

### Налаштування зйомки (графічний інтерфейс)

<!-- SCREENSHOT-NEEDED: Capture Settings pane (gear next to Capture All) with a connected array: capture-mode buttons (Single/Continuous/Interval), the bulk export-type toggle row, the Fastest Capture toggle, and the per-array group card showing the Aligned checkbox and the "Record index video" / "Record raw burst" buttons. -->

Іконка шестерні поруч із **«Зняти все»** відкриває панель налаштувань зйомки (потрібен відкритий проєкт — зняті дані зберігаються в ньому):

* **Режим зйомки**:**Одиночний**(один прохід) /**Безперервний**(послідовно; обмежується кількістю знімків, за замовчуванням 1, або тривалістю, за замовчуванням 10 с) /**Інтервал** (таймлапс: N знімків кожні X інтервалів, загалом Y; за замовчуванням — 1 знімок кожні 5 с протягом 1 хвилини).
* **Типи експорту для кожної камери**: Raw, Debayered, Radiance, Reflectance, Preview, Index — за замовчуванням увімкнено всі доступні опції. Radiance/Reflectance приховані для камер RGB-filter;**Reflectance з’являється лише тоді, коли камера має світловий датчик DAQ** (власний або успадкований від масиву); для Index потрібно налаштувати індексне вираження.
* **Вирівняно**(для масиву, за замовчуванням**увімкнено**): деформує експортовані дані членів масиву відповідно до профілю вирівнювання масиву, щоб експортовані дані були зареєстровані за пікселями. Raw завжди залишається невирівняним, але містить трансформацію в метаданих.
* **Найшвидше захоплення** (перемикач): лише необроблені дані + призначене значення DAQ + безкоштовний композитний індекс, пропускаючи математичні обчислення калібрування під час захоплення для досягнення максимальної швидкості — відновлення яскравості/відбиття/індексу здійснюється пізніше на основі збереженого `.daq`.
* Вибрані елементи зберігаються разом із проєктом. Приховані або призупинені камери пропускаються.

Еквівалент CLI (та сама кінцева точка бекенду, та сама семантика):

```bash
# One synced group, every applicable export level per camera (the default)
chloros-cli lattice array-capture -o output/

# Interval timelapse: one reflectance pass every 10 s for 5 minutes
chloros-cli lattice array-capture --interval 10 --duration 300 --processing reflectance -o timelapse/

# Fastest grab for a moving rig — raw + .daq now, calibrate later
chloros-cli lattice array-capture --fastest -o flightline/

# 30-second monitoring clip of the combined index view, plus a GIF
chloros-cli lattice array-record --duration 30 --fps 10 --gif -o monitoring/

# 5-second analysis-grade raw burst, then build the combined index video
chloros-cli lattice array-burst --duration 5 --build --products combined:index --fps 10 -o capture/
```

TIFF — стиснення знімків: `deflate` (без втрат, за замовчуванням) або `none` — повні таблиці прапорців, структура папки знімків та правила повторної обробки наведені в [Довідці щодо CLI](../reference/cli-reference.md#capture-modes-recorders--offline-reprocess).

## Підключення датчика освітлення DAQ

Для попереднього перегляду з корекцією відбиття та освітлення потрібні дані про світло, що падає зверху, від датчика DAQ (підключеного на вкладці **Датчики освітлення**):

* У **рядку масиву**на бічній панелі відображається**кнопка «DAQ · увімк./вимк.»** — вона *увімкнена*, коли встановлено датчик освітлення на рівні масиву **або** будь-яка камера в масиві має власний датчик; у підказці вказано, який саме датчик подає дані на яку камеру.
* Призначте датчик для всього масиву в налаштуваннях масиву → **Датчик навколишнього освітлення**→ випадаюче меню**Датчик освітлення**. Цей вибір зберігається разом із проєктом, поширюється на кожну камеру в масиві, але окремі камери все одно можуть замінити його власним датчиком.
* Рядок стану нижче відображає поточний стан: **Вимкнено**→ «Очікування першого спектра…» →**«Активно — освітлення для всіх камер у масиві скориговано»** → або, якщо за останні 3 секунди не надійшов новий спектр, повідомлення про застарілі дані — продовжується використання останнього зчитування (зчитування ніколи не втрачають чинності на шляху зйомки).

При призначеному датчику: стає доступним тип експорту «Відбивна здатність», попередній перегляд у реальному часі коригується з урахуванням освітлення, прогнозна автоматична експозиція може використовувати спектр, а кожне зчитування відбивної здатності записує фактично використане значення DAQ як **`.daq` sidecar** поруч із зображенням, щоб знімок можна було переобробити пізніше.

## Параметри `array-connect` CLI

| Параметр | За замовчуванням | Опис |
| --- | --- | --- |
| `--serials SN1,SN2,…` | автоматичне виявлення всіх камер LATTICE (потрібно ≥2) | **Перший послідовний порт є MASTER.** |

| `--wire-ceiling-mbps MB_PER_S` | auto-detected | Бюджет пропускної здатності хосту в МБ/с — форма CLI поля **Бюджет пропускної здатності**. Зменште це значення, якщо масив повідомляє про пошкоджені кадри. Зберігається разом із проєктом, тому при подальшому повторному підключенні воно відновлюється. |
| `--no-recommend` | вимкнено | Пропустити етап аналізу мережі. |
| `--no-ptp` | вимкнено | Вимкнути PTP (у цьому випадку мітки часу між камерами не можна порівнювати). |

`lattice array-list`, `array-status`, та `array-disconnect` керують постійним сеансом. Повний довідник підкоманд, включаючи вирівнювання (`align-calibrate` / `align-apply`) та мережеві інструменти, міститься в [Довідка по CLI § chloros-cli lattice](../reference/cli-reference.md#chloros-cli-lattice); еквіваленти SDK (`connect_array`, `ArraySession`, `attach_array`, `analyze_array_network`) наведені в [SDK Довідка](../reference/sdk-reference.md). Починаючи з Python, бюджет на кабелі становить `connect_array(..., wire_ceiling_mbps=120)`, а розподіл між активними пошкодженими та такими, що так і не надійшли, наведено в [`/api/camera/array/<id>/capability`](../reference/sdk-reference.md#array-health--which-subsystem-is-losing-frames).
