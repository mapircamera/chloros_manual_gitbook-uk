# Конвеєр обробки

ChlorosВерсія 1.2.0 використовує 4-потоковий конвеєр обробки, який працює за принципом поетапної конвеєрної лінії. Кожен потік відповідає за окрему фазу робочого процесу, тому одночасно на різних етапах можуть перебувати кілька зображень.

## Архітектура конвеєра

```

Images In → [Thread 1: Detection] → [Thread 2: Calibration] → [Thread 3: Processing] → [Thread 4: Export] → Files Out
```

Кожне зображення послідовно проходить усі чотири потоки. Завдяки багатопотоковій обробці Chloros+ кілька зображень одночасно обробляються в різних потоках — поки потік 3 обробляє одне зображення, потік 1 може виконувати розпізнавання наступного, потік 2 — калібрувати ще одне, а потік 4 — записувати готове зображення на диск.

Інформація про хід виконання передається для кожного потоку та транслюється через Server-Sent Events (бекенд публікує її на `/api/events`). У вікні відображення поточного прогресу в «CLI» чотири етапи позначені як **Виявлення, Аналіз, Обробка, Експорт**.***

## Деталі потоків

### Потік 1: Виявлення

**Мета**: Завантаження зображень та виявлення об’єктів калібрування.

* Зчитує файли зображень з диска — пари Survey3 `.raw`+`.jpg`, знімки LATTICE `.tif`/`.tiff` та `.dng`
* Витягує метадані EXIF (GPS, модель камери, мітки часу, експозиція)
* Виявляє калібрувальні мішені: геометрії мішеней, позначені ArUco, для знімків LATTICE, та класичний панельний детектор для фотографій калібрувальних мішеней Survey3
* Вихідні дані: дані зображення + метадані + результати виявлення мішеней

В основному це потік, що залежить від вводу-виводу та процесора.

### Потік 2: Калібрування

**Мета**: Обчислення параметрів калібрування на основі виявлених мішеней.

* Обчислює коефіцієнти калібрування відбиття на основі зображень мішеней
* Обчислює параметри корекції віньєтування
* Визначає калібрувальні криві для кожної смуги спектра
* Результати: параметри калібрування для кожного зображення

Обчислювальний потік, що залежить від процесора. Потік 3 очікує на його завершення, коли увімкнено калібрування відбиття, щоб коефіцієнти були готові до початку обробки будь-якого зображення.

### Потік 3: Обробка (GPU)

**Мета**: Застосування корекцій та обчислення індексів рослинності.**Це потік з найбільшою обчислювальною навантаженістю.*** **Дебейєринг**: перетворює RAW-дані Байєра на багатоканальні зображення
  * Стандартний (швидкий, середня якість) — за замовчуванням, `--debayer standard`
  * З урахуванням текстури (повільний, найвища якість) — лише для Chloros+, `--debayer texture-aware`, використовує модель шумозаглушення на основі ШІ/ML
  * Знімки LATTICE mono (M3M) є односмуговими: для них пропускаються етапи демозаїкування та балансу білого (з однорядковим повідомленням у журналі), тоді як будь-які зображення M3C/Bayer у тому самому циклі обробки все одно проходять ці етапи
* **Корекція віньєтування**: застосовує корекцію віньєтування об’єктива до всього зображення
* **Калібрування відбивної здатності**: застосовує калібрувальні коефіцієнти для перетворення в значення відбивної здатності
* **Розрахунок індексів**: обчислює індекси рослинності (NDVI, NDRE, GNDVI, …)
* Результати: оброблені дані зображення, готові до експорту

Цей потік найбільше виграє від прискорення за допомогою графічного процесора (GPU), і саме його налаштовує [Динамічна адаптація обчислень](dynamic-compute-adaptation.md).

### Потік 4: Експорт

**Мета**: запис оброблених зображень на диск.

* Записує вихідні файли у вибраному форматі — `TIFF (16-bit)`, `TIFF (32-bit, Percent)`, `PNG (8-bit)`, `JPG (8-bit)`
* Вбудовує метадані у вихідні файли (GPS, часові мітки, параметри обробки)
* Розміщує вихідні файли у папці проєкту у форматі `<camera>/<format>/<Product>_Images/` — наприклад, `LATT-M3M-L41-F550/tiff16/Reflectance_Calibrated_Images/`. **Експортовані файли зберігають ім’я вихідного файлу; папка ідентифікує продукт.**
* Для знімків LATTICE один вихідний кадр може розгалужуватися на кілька продуктів (Debayered, Preview, Radiance, Reflectance, Index), кожен у своїй власній папці продукту
* Результати: кінцеві файли на диску

В основному це потік, обмежений введенням-виведенням — використання SSD-накопичувача помітно покращує його продуктивність.

## Що під капотом: виконавці

У потоці 3 робота з кожним зображенням паралелізується за допомогою стандартного `concurrent.futures` з бібліотеки «Python»:

* **Стратегії використання GPU**(`GPU_SINGLE`, `GPU_PARALLEL`) використовують `ProcessPoolExecutor` із методом**spawn** — кожен робочий процес є окремим процесом із власним контекстом CUDA (`fork` успадковував би ініціалізований стан CUDA батьківського процесу та пошкоджував би дочірні процеси)
* **`CPU_PARALLEL`** використовує `ThreadPoolExecutor` — NumPy та OpenCV звільняють GIL, тому потоків достатньо
* Пристрої Jetson із 8 ГБ або менше спільної оперативної пам’яті повністю оминають виконавчий модуль і обробляють дані всередині процесу, послідовно
* Функція Texture Aware на графічному процесорі з об’ємом відеопам’яті менше 7 ГБ також працює послідовно — модель шумозаглушення не може вміститися більше ніж один раз

Chlorosне використовує жодних сторонніх фреймворків для розподілених обчислень (таких як Ray). Див. [Динамічна адаптація обчислень](dynamic-compute-adaptation.md), щоб дізнатися, як обираються стратегія та кількість робочих процесів.

## Послідовна обробка проти конвеєрної

### Вільний режим (послідовний)

У безкоштовній версії Chloros зображення обробляються **по одному**, послідовно проходячи всі чотири етапи:

```

Image 1: [Detect] → [Calibrate] → [Process] → [Export]
                                                         Image 2: [Detect] → [Calibrate] → [Process] → [Export]
```

У графічному інтерфейсі в безкоштовному режимі відображається спрощений індикатор прогресу; послідовні етапи позначаються як **Виявлення цілей**, а потім**Обробка**.

### Режим «Chloros» (конвеєрний)

З ліцензією «Chloros» усі чотири потоки працюють **одночасно** над різними зображеннями:

```

Thread 1: [Image 1] [Image 2] [Image 3] [Image 4] ...
Thread 2:           [Image 1] [Image 2] [Image 3] ...
Thread 3:                     [Image 1] [Image 2] ...
Thread 4:                               [Image 1] ...
```

Смуга прогресу в графічному інтерфейсі відображає чотири етапи; наведіть курсор на неї, щоб побачити прогрес для кожного потоку окремо. У консолі CLI ці самі чотири етапи транслюються в режимі реального часу як **Виявлення, Аналіз, Обробка, Експорт**.

{% hint style="info" %}
**Одна назва, дві назви.** У файлі «CLI» етап 3 називається _Processing_. У стрічці прогресу преміум-режиму бекенду — тій, яку відображає смуга прогресу в графічному інтерфейсі — цей самий етап позначений як _Calibrating_. Це один і той самий потік, який виконує одну й ту саму роботу (потік 3: дебейер, корекції, індекси).
{% endhint %}

{% hint style="success" %}
**Конвеєрна обробка з Chloros+** може бути у 3–5 разів швидшою за послідовну обробку, залежно від вашого обладнання та розміру набору даних. Найбільше прискорення спостерігається на системах із швидкими графічними процесорами та SSD-накопичувачами.
{% endhint %}

## Хід експорту в потоці 4

Потік експорту має власний механізм відстеження прогресу, який можна перевіряти окремо:**CLI:**

```bash
chloros-cli export-status
```

**SDK:**

```python
status = chloros.get_status()
print(f"Export: {status['export']['percent']}% - Phase: {status['export']['phase']}")
```

Обробка завершується, коли потік 4 досягає 100%.

{% hint style="info" %}
**Виконання, під час якого не записано жодного зображення, вважається невдалим.**У разі успіху `chloros-cli process` повідомляє, скільки зображень було записано (`Image products written: N`). Якщо були запрошені продукти, але**жодний**не був записаний — лише `project.json` та `calibration_data.json` — CLI виводить `Processing finished but wrote no image products.` та**завершує роботу з ненульовим кодом**, вказуючи назву папки проєкту та типові причини (вхідна папка не була розпізнана як захоплення — перевірте структуру та `--input-level` — або кожен запитуваний продукт був непридатний для цих камер). Скрипти можуть покладатися на код завершення.
{% endhint %}

## Зв’язок із динамічною адаптацією обчислень

[Динамічна адаптація обчислень](dynamic-compute-adaptation.md) насамперед впливає на **потік 3 (обробка)**:

* **`GPU_PARALLEL`**: Потік 3 одночасно обробляє кілька зображень на графічному процесорі за допомогою конвеєра `fused_gpu`
* **`GPU_SINGLE`**: Потік 3 серіалізує доступ до графічного процесора за допомогою семафора, тоді як робочі процеси перекривають операції вводу-виводу, використовуючи конвеєр `fused_gpu` або конвеєр `tiled_gpu`, що ефективно використовує пам’ять
* **`CPU_PARALLEL`**: Потік 3 використовує обробку на базі ЦП із багатопотоковим паралелізмом

Обсяг пам&#x27;яті графічного процесора, виділений для потоку 3, також збільшується по мірі завершення роботи потоків 1 і 2 — див. [Динамічне виділення пам&#x27;яті графічного процесора](dynamic-compute-adaptation.md#dynamic-gpu-memory-allocation).
