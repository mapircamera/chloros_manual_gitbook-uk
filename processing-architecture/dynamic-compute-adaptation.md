# Динамічна адаптація обчислювальних ресурсів У версії

Chloros
1.3.0 використовується функція виявлення апаратного забезпечення та автоматичний вибір стратегії обробки. Механізм обробки адаптується до вашого апаратного забезпечення — від Jetson Orin Nano до робочої станції з декількома графічними процесорами — без будь-якого ручного налаштування.

***

## Як це працює

Під час запуску Chloros
виконує профілювання вашої системи:

1. **Виявляє операційну систему** — Windows
або Linux
2. **Визначає ядра процесора та загальний обсяг оперативної пам’яті**

3.**Виявляє наявність графічного процесора** — підтримку NVIDIA CUDA, обсяг відеопам’яті (VRAM), модель
4. **Визначає модель Jetson** (якщо є) — через `/proc/device-tree/model`
5. **Перевіряє теплові датчики** (Jetson) — для обробки з урахуванням температури
6. **Вибирає стратегію обчислень** — на основі всього виявленого апаратного забезпечення
7. **Автоматично налаштовує кількість робочих процесів, тип конвеєра та розподіл пам’яті**

Виявлений профіль кешується для сеансу в пам’яті та на диску, завдяки чому наступні запуски відбуваються швидше:

| Платформа | Кешований профіль |
| --- | --- |
| **Linux
/ Jetson** | `~/.config/chloros/system_config.json` (враховує `XDG_CONFIG_HOME`) |
| **Windows** | `%LOCALAPPDATA%\Chloros\config\system_config.json` |

Видаліть цей файл, щоб змусити систему виконати нове виявлення — це корисно після додавання графічного процесора (GPU) або збільшення обсягу оперативної пам’яті. Chloros
також автоматично виконує повторне виявлення, якщо кеш було записано несумісною старою версією.

## Стратегії обчислень

Chloros
обирає одну з трьох стратегій обчислень на основі вашого апаратного забезпечення:

| Стратегія | Вибирається, коли | Робочі процеси | Виконавець | Конвеєр |
| --- | --- | --- | --- | --- |
| **`GPU_PARALLEL`**| Графічний процесор CUDA з**12 ГБ+ відеопам’яті**(у єдиній пам’яті Jetson, також потрібно 12 ГБ+ загальної спільної оперативної пам’яті) | `min(4, ⌊(VRAM − 0.5GB) × 0.9 ÷ 3.5GB⌋)`, мінімум 2 —**обмежено до 2 на Jetson** | Робочі процеси (окремі контексти CUDA) | `fused_gpu` |
| **`GPU_SINGLE`**| Графічний процесор CUDA з**2–12 ГБ відеопам’яті**| 3 (перекриття вводу-виводу; доступ до графічного процесора серіалізується семафором).**1 (послідовно) на Jetson з об’ємом оперативної пам’яті менше 12 ГБ** | Робочі процеси (окремі контексти CUDA); послідовне виконання в межах одного процесу на Jetson з малим об’ємом оперативної пам’яті | `fused_gpu` / `tiled_gpu` |
| **`CPU_PARALLEL`** | Без CUDA-графічного процесора або з об’ємом відеопам’яті менше 2 ГБ | `max(2, physical cores − 1)` | `ThreadPoolExecutor` | `cpu_fallback` |

Приклади розрахунку кількості робочих процесів за формулою `GPU_PARALLEL`: 12 ГБ відеопам&#x27;яті → 2 робочих процеси, 16 ГБ → 3 робочих процеси, 20 ГБ і більше → 4 робочих процеси. Кожному робочому процесу виділяється 3,5 ГБ — це виміряна потреба завдання з підтримкою текстур — у межах 90 % від обсягу відеопам&#x27;яті, що залишився після резерву в 0,5 ГБ.

{% hint style="info" %}
**Стратегії для графічних процесорів вимагають версії PyTorch, здатної використовувати CUDA.** Машина, на якій PyTorch не має придатного для використання CUDA-пристрою, отримує `CPU_PARALLEL`, незалежно від типу її графічного процесора. Пакет Jetson 1.3.0 використовує збірку PyTorch для CUDA з JetPack 6, тому Jetson відповідає вимогам після встановлення бібліотек CUDA та cuDNN з JetPack. Jetson з об’ємом оперативної пам’яті менше 12 ГБ завжди обробляє одне зображення за раз, у процесі роботи (що реєструється як `GPU_SINGLE`).
{% endhint %}

Стратегії на базі GPU запускають пул робочих процесів, кожен з яких є окремим процесом ОС із власним контекстом CUDA; Chloros
запускає їх, знову запускаючи власну встановлену програму-бекенд (а не через `multiprocessing` у Python
, запуск робочих процесів у якому не працює всередині упакованого додатка). Стратегія на базі ЦП використовує пул потоків (Python
`ThreadPoolExecutor`). Chloros
не використовує жодних сторонніх фреймворків для розподілених обчислень (таких як Ray).

### Типи конвеєрів

* **`fused_gpu`** — Повний шлях обробки на GPU. Операції дебейєрингу, корекції та індексації виконуються на GPU в одному злитому проході. Найвища пропускна здатність, вимагає найбільшого обсягу VRAM.
* **`tiled_gpu`** — Конфігурація з ефективним використанням пам’яті GPU. Обробляє зображення частинами, щоб вміститися в обмежену пам’ять GPU. Нижча пропускна здатність, але працює на пристроях з обмеженою пам’яттю.
* **`cpu_fallback`** — Обробка виключно на ЦП із використанням багатопотокового паралелізму. Використовується, коли графічний процесор NVIDIA недоступний, а також як крайній варіант у разі збою обох шляхів обробки на графічному процесорі.

Ланцюжок резервних варіантів під час виконання завжди має вигляд `fused_gpu` → `tiled_gpu` → `cpu_fallback`.

## Ручне перевизначення стратегії

Встановіть змінну середовища `CHLOROS_STRATEGY`, щоб примусово застосувати певну стратегію — це експертний «запасний вихід» на випадок, коли автоматичне виявлення обирає щось невідповідне для вашої ситуації (наприклад, щоб залишити графічний процесор вільним для інших завдань):

```bash
# Valid values: CPU_PARALLEL, GPU_SINGLE, GPU_PARALLEL
CHLOROS_STRATEGY=CPU_PARALLEL chloros-cli process ~/datasets/flight001
```

Збіг імені змінної визначається без урахування регістру; все, що не є одним із трьох імен, ігнорується, і автоматичне визначення продовжується у звичайному режимі. У разі перевизначення Chloros
все одно обирає кількість робочих процесів за вас:

| Перевизначення | Кількість робочих процесів |
| --- | --- |
| `CPU_PARALLEL` | `max(2, physical cores − 1)` |
| `GPU_SINGLE` | 3 |
| `GPU_PARALLEL` | `min(4, physical cores)` |

Перезапис `GPU_SINGLE` або `GPU_PARALLEL` на машині без придатного пристрою CUDA відхиляється з записом `[STRATEGY]` у журналі, і для виконання використовується `CPU_PARALLEL`.

Рекомендується встановлювати це на рівні кожної команди, а не постійно, щоб звичайні запуски продовжували автоматично адаптуватися.

## Поведінка, специфічна для платформи

| Платформа | Стратегія | Робочі процеси | Конвеєр | Примітки |
| --- | --- | --- | --- | --- |
| **Jetson Orin Nano 8 ГБ** | `GPU_SINGLE` | 1 | `tiled_gpu` (послідовний) | Режим ефективного використання пам’яті, по одному зображенню за раз |
| **Jetson Orin NX 8 ГБ** | `GPU_SINGLE` | 1 | `tiled_gpu` (послідовна) | Спільна оперативна пам’ять менше 12 ГБ змушує використовувати послідовну обробку |
| **Jetson Orin NX 16 ГБ** | `GPU_PARALLEL` | 2 | `fused_gpu` (паралельна) | Рекомендований периферійний пристрій — обмеження Jetson: 2 робочі процеси |
| **Jetson AGX Orin 32–64 ГБ** | `GPU_PARALLEL` | 2 | `fused_gpu` (паралельна обробка) | Максимальна продуктивність на периферії (також обмеження Jetson — 2 робочі процеси) |
| **Настільний ПК з 8 ГБ відеопам&#x27;яті** | `GPU_SINGLE` | 3 | `fused_gpu` / `tiled_gpu` | 3 робочі процеси перекриваються у введенні-виведенні, тоді як семафор серіалізує доступ до графічного процесора |
| **Настільний ПК з графічним процесором 12 ГБ+** | `GPU_PARALLEL` | 2–4 | `fused_gpu` (одночасні) | Оптимальна продуктивність настільного ПК: 12 ГБ → 2 робочі процеси, 16 ГБ → 3, 20 ГБ+ → 4 |
| **Система лише з ЦП** | `CPU_PARALLEL` | фізичних ядер − 1 (мін. 2) | `cpu_fallback` | Графічний процесор не потрібен, використовується пул потоків |

{% hint style="info" %}
**Уніфікована пам’ять Jetson**: пристрої Jetson спільно використовують пам’ять графічного процесора та центрального процесора. Jetson Orin NX з 16 ГБ повідомляє про ~15,3 ГБ відеопам’яті (VRAM), але це та сама фізична оперативна пам’ять, яку використовують ОС та процеси центрального процесора. Саме тому пристрої Jetson з об’ємом пам’яті 16 ГБ і більше відповідають вимогам `GPU_PARALLEL`, як і настільні графічні процесори з об’ємом 12 ГБ і більше, проте їхня кількість робочих процесів обмежена двома — графічний процесор, робочі процеси та їхні контексти CUDA для кожного робочого процесу використовують один і той самий спільний пул.
{% endhint %}

### Бюджет графічного процесора за обсягом VRAM (дискретні графічні процесори)

На хостах x86_64 з дискретним графічним процесором NVIDIA виявлений обсяг VRAM також визначає, скільки ресурсів може задіяти обробка на карті та наскільки великими можуть бути пакети:

| Виявлений обсяг VRAM | Верхня межа бюджету графічного процесора | Множник розміру пакета |
| --- | --- | --- |
| **8 ГБ і більше** | 90% | ×2,0 |
| **6–8 ГБ** | 85% | ×1,75 |
| **3,5–6 ГБ** | 80 % | ×1,5 |
| **2–3,5 ГБ** | 75 % | ×1,25 |
| **Менше 2 ГБ** | 70 % | ×1,0 |

Дискретні графічні процесори резервують для системи лише 0,5 ГБ, оскільки вони не використовують системну оперативну пам’ять. Профілі Jetson резервують значно більше і мають нижчі обмеження — див. [Посібник NVIDIA Jetson](../linux/nvidia-jetson-guide.md#per-model-gpu-budget).

## Динамічний розподіл пам’яті графічного процесора

Chloros
використовує [4-потоковий конвеєр обробки](processing-pipeline.md):

* **Потік 1** (Виявлення) — Завантаження зображення, аналіз EXIF, виявлення об’єкта
* **Потік 2** (Калібрування) — обчислення калібрування відбиття
* **Потік 3** (Обробка) — дебейер на графічному процесорі, корекція віньєтування, обчислення індексу
* **Потік 4** (Експорт) — запис файлів, вбудовування метаданих

Потоки 1, 2 та 4 споживають мало ресурсів графічного процесора; Потік 3 є найбільш ресурсоємним. У міру завершення роботи попередніх потоків конвеєра їхній ресурс графічного процесора **перерозподіляється між рештою активних потоків**, тому потік 3 отримує дедалі більше пам’яті в міру просування процесу.

### Етапи розподілу ресурсів

| Етап | Активні потоки | Розподіл пам’яті графічного процесора |
| --- | --- | --- |
| **Ранній** | 1, 2, 3, 4 | Розподіляється між усіма потоками, більша частина — потоку 3 |
| **Середньо-ранній** | 2, 3, 4 | Частка потоку 1 перерозподіляється |
| **Середина-кінець** | 3, 4 | Частки потоків 1 і 2 перерозподіляються між 3 і 4 |
| **Кінець** | 3 або 4 | Останній активний потік отримує максимальний обсяг пам’яті |

Ці цифри визначаються двома правилами:

* Потік, який є **єдиним** активним, отримує максимальний обсяг, передбачений його профілем.
* Коли активними є кілька *важких* завдань GPU, базовий обсяг кожного з них розподіляється між ними (ніколи не нижче встановленого мінімуму).

Значення, яке фактично використовується під час виконання, є **меншим** із двох: виділення, задане в профілі платформи, та поточна рекомендація від монітора пам’яті графічного процесора, тому завантажена карта завжди має пріоритет над оптимістичним профілем.***

## Обробка з урахуванням текстур

Дебейер з підтримкою текстур (**лише Chloros
+** — `--debayer texture-aware`) запускає модель шумозаглушення на основі ШІ/машинного навчання, яка потребує приблизно 1,75 ГБ VRAM у форматі FP16 на кожну копію, тому вона використовує набагато більше пам’яті графічного процесора, ніж стандартний метод:

* Системи з **менше 7 ГБ VRAM**обробляють «з урахуванням текстур» у**синхронному циклі, по одному зображенню за раз** — кілька копій моделі не вмістяться, а пул робочих процесів лише посилить конфлікти доступу
* Системи з **7 ГБ і більше VRAM** можуть обробляти Texture Aware паралельно, хоча й із меншою кількістю робочих процесів порівняно зі стандартним методом
* На **Jetson** обробка Texture Aware завжди прив’язана до одного робочого процесу
* За **відсутності придатного для використання графічного процесора з підтримкою CUDA** під час виконання використовується стандартний дебейер, а бекенд записує в журнал один рядок `[DEBAYER] … needs a CUDA GPU …` із поясненням причини
* На енергоефективних пристроях Jetson (Nano, Orin Nano) CLI
застосовує обмеження частоти графічного процесора при запиті на використання Texture Aware — див. [Посібник NVIDIA Jetson](../linux/nvidia-jetson-guide.md#gpu-frequency-cap-for-texture-aware-on-nano-and-orin-nano)

## Управління тепловим режимом (Jetson)

Пристрої Jetson мають обмеження щодо температури, особливо в закритих приміщеннях або під час використання в літальних апаратах. Chloros
відстежує вбудовані датчики температури Jetson і автоматично масштабує розміри пакетів:

| Температура | Реакція |
| --- | --- |
| **&lt; 70 °C** | Нормальна робота — повна швидкість |
| **70 °C** (Попередження) | Розмір пакета поступово зменшується (від 100 % до 50 % у діапазоні від 70 °C до 80 °C) |
| **80 °C** (Критичний) | Агресивне обмеження продуктивності (50 % → 0 % у діапазоні від 80 °C до 90 °C) |
| **90 °C** (Вимкнення) | Повне припинення обробки на графічному процесорі |

На настільних системах з належним охолодженням терморегулювання спрацьовує рідко.

## Управління навантаженням на пам&#x27;ять

Програма Chloros
постійно відстежує стан пам&#x27;яті графічного процесора під час обробки та реагує на трьох рівнях.

**Розмір пакета.** Партія починається з 8 зображень, помножених на коефіцієнт платформи з таблиць вище. Потім Chloros
перевіряє вільний обсяг VRAM, резервує 20 % його для власних накладних витрат PyTorch і припускає, що на одне зображення розміром 12 МП припадає приблизно 100 МБ пам’яті графічного процесора — розмір партії визначається меншим із двох значень: обмеженням, виведеним з обсягу пам’яті, або базовим значенням для платформи. Він ніколи не опускається нижче 1.

**Превентивне зменшення.**При**використанні VRAM понад 85%** розміри партій зменшуються до того, як виникнуть збої.**Обмеження виділення пам’яті на кожен потік.** У міру зростання поточного завантаження бюджет графічного процесора для кожного потоку зменшується: ×0,75 при завантаженні понад 80%, ×0,5 — понад 90%. Діапазони моніторингу становлять 70% (консервативний), 85% (нормальний робочий ліміт) та 95% (ризик нестачі пам’яті).**Відступ та відновлення після нестачі пам’яті.** Якщо все ж таки трапляється подія нестачі пам’яті:

* розмір пакета **зменшується вдвічі**, а при кожному наступному випадку нестачі пам’яті — ще раз удвічі; кожний наступний успішний пакет зменшує це обмеження на один крок
* обсяги виділення пам’яті для активних потоків скорочуються до 70% від поточного значення, а алгоритм виділення переходить на консервативну стратегію, знову послаблюючи обмеження після серії успішних виділень
* за умов значного навантаження конвеєр переходить з `fused_gpu` на `tiled_gpu`, а в крайньому випадку — на `cpu_fallback`

**Оперативна пам’ять хоста (Jetson).** Перед обробкою CLI
оцінює піковий обсяг пам’яті хоста на основі кількості зображень та режиму дебейєрингу й попереджає, якщо оперативної пам’яті та файлового обміну, ймовірно, недостатньо, виводячи точні команди для додавання обміну — див. [Посібник NVIDIA Jetson](../linux/nvidia-jetson-guide.md#swap-warning-and-recommendations).

## Моніторинг адаптації обчислювального рівня

### Діагностика системи

`chloros-cli selftest` — це найшвидший спосіб перевірити, що бачить обчислювальний рівень:

```bash
chloros-cli selftest
```

Його 7 перевірок охоплюють версію, доступність портів, запуск бекенду, `/api/test`, інформацію про систему, наявність моделі шумозаглушувача та готовність CUDA + шумозаглушувача. Перевірка 5 безпосередньо виводить рядок апаратного забезпечення:

```
      GPU: NVIDIA RTX A4000, CUDA: True, PyTorch: 2.7.0
```

Перевірка 7 виводить `CUDA: <bool>, Denoiser: <bool>` — обидва параметри повинні бути істинними, щоб Texture Aware взагалі можна було використовувати.

### Журнали бекенду

Стратегія та кількість робочих процесів обираються всередині бекенду на початку кожного запуску — у командному рядку (CLI
) немає банера, який би їх повідомляв. Коли щось поводиться несподівано (перехід на резервний шлях GPU, OOM, шумопоглинач, що не завантажується), це відображається у журналі бекенду для цієї сесії:

| Платформа | Розташування журналу |
| --- | --- |
| **Linux
/ Jetson** | `~/.cache/chloros/logs/backend_<YYYYMMDD_HHMMSS>.log` (один файл на кожен запуск) |
| **Linux
, бекенд, запущений через CLI** | також `~/.chloros/backend.log` |
| **Windows** | `%LOCALAPPDATA%\Chloros\logs\` |

### Прогрес у реальному часі

Під час виконання CLI
показує прогрес у реальному часі для кожного потоку (виявлення, аналіз, обробка, експорт), що передається через Server-Sent Events — це практичний спосіб перевірити, чи є потік 3 вузьким місцем. Див. [Конвеєр обробки](processing-pipeline.md).
